## 1. Summary

Three deliverables share one Go monorepo:

1. **Agent** (`librepatch-agent.exe`): a Go Windows service running as SYSTEM. It opens one outbound mTLS gRPC stream to the server and never listens on a port. It runs only a fixed set of typed jobs, and each job must be signed by the server's job-signing key and bound to this device. It runs installers itself, using winget manifests only as metadata. User-scope work runs in a short-lived helper process inside the target user's session. The helper talks to the service only over an anonymous pipe that the service hands to it at launch.
2. **Server** (`librepatch-server`): one Go binary that contains:
   - the REST API (OpenAPI-first);
   - the embedded React GUI;
   - the agent gateway, which terminates mTLS itself and is never put behind the reverse proxy;
   - the deployment scheduler, the winget catalog sync, the internal CA and the job signer.

   It is shipped as a distroless container and runs alongside Postgres and Caddy in `docker-compose`.
3. **Web GUI**: React, TypeScript, Vite and Mantine. It gets live job status over Server-Sent Events.

## 2. Stack (with the challenges I'm making)

| Area | Choice | Notes / challenge to the brief |
|---|---|---|
| Agent language | **Go** (current stable, pinned in `go.mod` `toolchain`) | Agree with the brief. Rust would give a smaller binary and lower memory use. But WUA/COM and WinRT are no easier from Rust, and sharing protocol, signing and version-comparison code with the server is a big maintainability win. **Gate:** if the agent exceeds 15 MB or 30 MB RSS at the end of Phase 1, I'll report it and propose fixes before going further. |
| Agent transport | **gRPC bidirectional stream over TLS 1.3 + mTLS**, protobuf messages | Gives typed messages, flow control, keepalives and deadlines out of the box. Each message type is versioned. If grpc-go pushes the binary past budget, the framing layer is isolated, so it can be swapped for protobuf-over-WebSocket. |
| Agent local state | **bbolt** (pure Go, small) | Holds the job queue, result outbox, inventory snapshot and executed-job ledger. |
| Server | **Go**: chi (REST), grpc-go (gateway), pgx + **sqlc** (typed, parameterized SQL only), goose (embedded migrations) | |
| API contract | **OpenAPI 3.0 spec-first** (`api/openapi.yaml`), server stubs plus request validation generated by oapi-codegen, TS client generated for the GUI | Writing the spec first means validation is generated, not hand-written. |
| Database | **PostgreSQL 16+** | **Challenge:** I recommend *dropping the SQLite dev mode*. Supporting two SQL dialects doubles query maintenance and hides bugs. Dev mode is `docker compose -f compose.dev.yml up`, which starts a throwaway Postgres in one command. |
| GUI | React + TS + Vite, **Mantine** (MIT), TanStack Query/Table, React Router | Mantine supports CSP nonces. That lets us run a strict CSP with no `unsafe-inline`. |
| Live updates | **SSE** | One-directional by nature, works through Caddy, uses the cookie-auth session, easier to secure than WebSockets. |
| Reverse proxy | **Caddy** for the GUI/API only (ACME, or `tls internal` / admin-provided certs for LAN) | The agent gateway is published directly on its own port (default 8443). We never want a proxy to authenticate client certificates or forward them in headers. |
| Agent installer | MSI | **Decision for you:** WiX v6+ requires its [Open Source Maintenance Fee](https://docs.firegiant.com/wix/osmf/) for commercial use (from US$10/month). The alternatives are pinning WiX v5 (no fee, but no future fixes) or `msitools`/`wixl`. I'll default to WiX and flag it in Phase 5. |
| Supply chain | Go modules pinned plus `go.sum`, npm lockfile, Dependabot, govulncheck, gosec, semgrep, `npm audit`, Syft SBOM, cosign for images, Authenticode for Windows binaries | |

## 3. Assumptions made on your behalf (please confirm or override)

You dismissed the clarifying questions, so I went with these defaults. Changing any of them later is cheap now and expensive after Phase 1.

1. **Source model: open source, AGPL-3.0 (D100; first planned as proprietary and closed).** Shipped dependencies may only use permissive licenses (MIT, BSD, Apache-2.0, ISC; MPL-2.0 at file level), enforced by a license check in CI, so everything stays compatible with the AGPL.
2. **Minimum Windows: Windows 10 1809+ / Windows 11 / Server 2019+.** This is what current Go supports and what winget-manifest and MSIX installs need. Server 2016 can be added later for MSI/EXE only. Server 2012 R2 would mean leaving Go.
3. **Scale target: up to ~10k devices per installation** on one server container. The gateway is designed so it can be split out later, and Phase 6 includes a load test with 10k simulated agents.
4. **Repository:** the previous Brick Breaker game has been deleted, as you instructed.

Owner decisions (resolved and still open) are tracked in [DECISIONS.md](DECISIONS.md#owner-decisions).

## 4. Phased roadmap

Every phase ends with the same **Definition of Done**:

- it builds cleanly, tests pass, and the linter and security scanners are clean;
- a fresh `docker compose up` works following only the README;
- the docs are updated and known gaps are listed honestly;
- there is a demo script for a real test VM.

I stop for review after each phase.

### Phase 1: Foundations
- Repo scaffolding, CI (lint, test, govulncheck, gosec, semgrep, license check, SBOM), Makefile.
- Postgres schema v1 (orgs, sites, users, sessions, devices, certs, enrollment tokens, audit log), goose migrations, sqlc.
- Internal PKI:
  - an offline-style root, encrypted with a passphrase you set at first run;
  - an online agent-issuing intermediate;
  - a separate job-signing certificate issued directly by the root.
- First-run setup: admin account with a strong password, mandatory TOTP enrollment, and recovery codes. There are no default credentials.
- Session auth, CSRF protection, security headers and CSP, login rate limiting and lockout, RBAC skeleton, audit-log writer (hash-chained, insert-only database role).
- Enrollment tokens (limited use, expiring, optional admin approval) and the enrollment endpoint (agent sends a CSR, the key never leaves the device).
- mTLS gRPC gateway: hello, heartbeat, reconnect with backoff and jitter, immediate cut-off on revocation, certificate renewal.
- Agent: Windows service, enrollment, client key in CNG (TPM-backed when available, otherwise a non-exportable software KSP key), heartbeat, basic hardware/OS inventory.
- GUI: setup wizard, login with MFA, device list, enrollment-token management, revoke and approve devices.
- docker-compose: Caddy, server and Postgres, hardened (non-root, read-only filesystem, all capabilities dropped, no database port published, healthchecks).
- Tests:
  - unit tests;
  - an integration test that runs the real agent core, with fake Windows collectors, against the real server in compose (Linux CI);
  - a Windows CI job that runs the real Windows agent against a natively started server and the runner's Postgres.

**Exit demo:** run `docker compose up`, complete setup with MFA, create a token, install the agent on a VM, see it appear live, revoke it, and watch it disconnect immediately.

### Phase 2: Inventory
- Software inventory from:
  - HKLM 64-bit and 32-bit, plus each loaded HKU;
  - offline profiles via `RegLoadAppKey` on a private copy of the hive (never the original);
  - MSI product codes;
  - AppX/MSIX for all users;
  - winget portable packages.

  Every row is tagged with scope and owning SID.
- Event-driven change detection with `RegNotifyChangeKeyValue`, debounced and diffed into deltas, plus a daily low-priority reconcile. Revision-based delta protocol with resync.
- Hardware extensions: BitLocker, disks, pending reboot, uptime, last logged-on user, device users and profiles.
- Server:
  - software title normalization and a sortable version key;
  - fleet-wide search ("who has X, which versions");
  - device detail pages;
  - dynamic groups via a typed filter AST compiled to parameterized SQL;
  - CSV export with formula-injection escaping.

**Exit demo:** install and uninstall apps machine-wide and per user on a VM with two users, and watch the deltas arrive within about a minute.

### Phase 3: Software deployment *(implemented; see docs/ARCHITECTURE.md §0 for what is verified, and docs/demos/PHASE3-DEMO.md)*
- Catalog: winget index sync with signature verification, package search and import, version and installer metadata, `verified` flag, admin overrides (silent args, detection rules, version pinning, exclusions), and custom package upload (content-addressed).
- Signed job envelopes, local verification, replay ledger.
- Install engine:
  - download, then SHA-256 check, then Authenticode check, all in a protected staging directory;
  - per-installer-type argument builders (MSI, MSIX, Inno, NSIS, Burn, EXE, portable, zip-nested);
  - Job Object process-tree tracking, exit-code maps, timeouts, retries;
  - detection rules per scope.
- User-context helper (`WTSQueryUserToken` + `CreateProcessAsUser` + inherited anonymous pipe), logon-triggered queue ("waiting for user logon"), and the per-user app policy (Report only / Update in place / Convert to machine-wide / Remove).
- Self-updating app detection and policy.
- Deployments: targets, schedule, live status over SSE, per-device result log.
- The VM test matrix (see ARCHITECTURE §7.9) runs before any package is marked as supported.

### Phase 4: Windows and driver updates *(implemented; see docs/ARCHITECTURE.md §0, SECURITY §9c and docs/demos/PHASE4-DEMO.md. WUA and restart paths are unverified on real Windows)*
- WUA COM: scan (software and drivers, choice of WU, Microsoft Update or managed server), download, install, hide/unhide, reboot detection.
- Update catalog on the server, approval rules (classification, severity, delay days), manual approve or decline.
- Rings (pilot, then broad, with success thresholds), maintenance windows evaluated on the device, reboot policy (never, outside active hours, deadline with a user notice through the session notifier), and detection of conflicting WSUS/WUfB policy.

### Phase 5: Automation and polish *(implemented; see docs/ARCHITECTURE.md §0, SECURITY §9d and docs/demos/PHASE5-DEMO.md. Self-update, the MSI and WebAuthn on real hardware are unverified on real Windows)*

- Agent self-update: vendor release-key signature plus Authenticode, A/B slots, health-confirmed promotion with automatic rollback.
- `librepatch-server backup` / `restore`: encrypted with age, version-checked.
- Agent MSI with silent-install properties for GPO, Intune or an RMM.

### Phase 6: Hardening and release *(implemented; see docs/SECURITY.md §9e–§9g, docs/LOADTEST.md and docs/demos/PHASE6-DEMO.md. The release workflow, Authenticode/KMS/Sigstore steps and the Windows-side fixes are unverified)*

## 5. Biggest risks I see up front

1. **Server compromise means fleet compromise.** This is inherent in any RMM-style product. The mitigations are in SECURITY.md §6: an agent-side policy limit the server can't raise, vendor-signed agent updates, four-eyes approval for large deployments, and HSM/PKCS#11 support for the signing key later.
2. **The winget community repository is a supply-chain input.** Hashes protect us *after* import, but not against a malicious manifest upstream. The mitigations are signer pinning with alerts when the signer changes, the `verified` flag, and a delay for new versions in auto-update rings.
3. **Per-user installs are messy.** Installer behaviour varies by vendor, so "supported" means an app has passed the VM matrix, not just that a manifest exists.
4. **WUA behaves differently across machines** under WSUS/WUfB/GPO policies. We'll detect and report conflicts rather than fight them.
5. **Agent footprint vs. features.** Size and memory are measured in CI from Phase 1, with a budget that fails the build.
